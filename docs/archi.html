MedLedger · Patient‑Controlled Vault

Cryptographic health data platform — private keys never leave the client, every grant is signed, DEKs always wrapped.
Five Non‑Negotiable Invariants
Private keys never leave the client. Generated client-side, never transmitted.
Server stores only public material. Public keys, encrypted records, permission signatures — no plaintext.
On‑chain data is minimal. Only public key registrations, grant hashes — no health data.
Every permission grant = signed data structure. ECDSA signature verified before persistence.
DEKs are always ECIES‑wrapped. Record Encryption Keys never exist server-side in plaintext.

Core Data Flows
Registration & Login Flow
1Client POST email + password → server hashes with PBKDF2 (100k iter, salt)
2Inactive user record + verification token (email simulation)
3Client verifies token → server generates P-256 keypair via KeyManager
4Stores public_key_hex + hash; private_key_pem returned once → never stored
5Login: password verification (constant‑time), JWT HS256 issued (sub, email, exp)
File Upload (DEK + ECIES)
1Client sends private_key_pem + file → server derives owner public key
2Generate fresh 256‑bit DEK, AES-256-GCM encrypt file → IV + ciphertext
3ECIES-wrap DEK under owner's public key → dek_bundle
4Atomically store VaultRecord + CiphertextRecord (DEK never in plaintext)
5Return record_id — plaintext DEK zeroed immediately after wrapping
🔒 DEK always wrapped, forward secrecy per file via ephemeral ECIES keys
Grant + Access Flow
1Owner POSTs private_key + grantee public_key + record_id + permission
2Server decrypts DEK via owner private key (ECIES) → re‑encrypts under grantee public key → new bundle
3Construct canonical permission payload → sign with owner's private key (ECDSA P‑256)
4Grant stored: dek_bundle_grantee + signature_hex + time_window + revoked=false
5On grantee download: verify signature, check time window, decrypt DEK bundle → plaintext DEK locally
Revoke: grant.revoked = True → future checks instantly reject
Security Properties & Threat Model
AES-256-GCM + ECIES ECDSA non‑repudiation Shamir 3-of-5 recovery
✅ Defeats: database breach (ciphertext only), server compromise (no private keys), permission forgery (signature verification), insider access, replay via signed time windows.
🔐 Cryptographic guarantees: Forward secrecy (fresh ephemeral keypair per ECIES), constant‑time password verify, PBKDF2 brute‑force resistance.
Every grant is a signed data structure — rows without valid signature are invalid.
Data Model & Strict Separation
File Split (Identity vs Vault)
data/users.json → UserRecord: id, email, password_hash, public_key_hex, public_key_hash, is_active, last_login
❌ never contains ciphertext, DEK bundles, grants
database/vault.json → VaultRecord, CiphertextRecord, Grant, Audit entries
🔒 encrypted vault state, DEK bundles, grants, signatures
Rationale: identity never co-resides with encrypted medical records — deliberate isolation.
Core Schema Classes
  • UserRecord — id, email, username, role, password_hash, public_key_hex, verification_token
  • VaultRecord — record_id (UUID), owner_key_hash, filename, iv_hex, tags, created_at
  • CiphertextRecord — record_id FK, ciphertext bytes, dek_bundle (ECIES encrypted for owner)
  • Grant — grant_id, record_id, grantor_hash, grantee_public_key, permission_level, time_window, dek_bundle_grantee, signature_hex, revoked flag
  • AuditEntry / VaultAuditEntry — immutable action trails

Production SSI Mode
Private key never transmitted — In production (self‑sovereign identity) all key generation happens client‑side.
Server only stores public keys and encrypted payloads.
JWT auth + ECDSA grants = zero‑trust ready.
Shamir fragments enable key recovery without central escrow.
Threat Model Summary
Database breach
Ciphertext + encrypted DEKs → useless without private key
Server compromise
Private keys never transmitted (SSI mode) → only public material
Permission forgery
ECDSA signature on grant; invalid rows rejected
Replay / expired grants
Signed time window enforces expiry
Patient controls master private key — no central party can revoke access to patient’s own records.
