# MedLedger Authentication Specification

**Version:** 2.1 | **Date:** June 2026 | **Status:** Current — Reflects Deployed System

**Architecture (Actual):** Bearer JWT in Authorization header + opaque refresh token
**Architecture (Planned hardening):** BFF + HttpOnly Cookies + CSRF (see §9)

---

## 1. Current Implementation vs Original Plan

The original v2.0 spec proposed a cookie-based BFF pattern. The deployed system uses **Bearer tokens in the `Authorization` header**, managed by frontend JavaScript. This document describes what is actually running. The cookie-based hardening remains the recommended next step — see §9.

| Decision | Originally Planned | Actually Implemented |
|----------|--------------------|-----------------------|
| Token delivery | HttpOnly cookie | `Authorization: Bearer <token>` header |
| CSRF protection | Double-submit cookie | Not applicable (no cookies = no CSRF surface for API calls) |
| Registration | Two steps (create account, then POST keys separately) | One step — keys included in `/auth/register` body |
| TOTP | Planned removal (keypair = 2FA) | **Retained** — optional second factor, fully implemented |
| Password reset | Planned removal (no recovery) | **Retained** — 6-digit email code flow exists |
| Password hashing | Argon2id (target) | Argon2id (active), PBKDF2 verify-and-rehash for legacy |

**Why Bearer tokens instead of cookies:** Simpler to implement with no CORS cookie complexity, easier local development. The trade-off is JS-accessible tokens are vulnerable to XSS for their lifetime (15 min for access token). This is an accepted risk for the current phase, with cookie migration planned.

**Why TOTP and password reset were kept:** The "keypair-only" model was found to create too much support burden in practice — losing access to Layer 1 (account) when only Layer 2 (keypair) should be at risk was considered bad UX. TOTP and password reset only ever affect Layer 1; Layer 2 (the vault) remains genuinely non-recoverable.

## 2. Token Specification (Actual)

### 2.1 Access Token (JWT)

Issued by `TokenModule.create_access_token()`. Sent by the client as:

```
Authorization: Bearer <jwt>
```

| Claim | Description |
|-------|-------------|
| `sub` | user_id_hex |
| `username` | For display |
| `email` | For display |
| `iat` | Issued at |
| `exp` | Expires at (15 minutes from iat) |

Verified by `routes/deps.py:get_current_user` on every protected route.

### 2.2 Refresh Token (Opaque)

| Property | Value |
|----------|-------|
| Format | Random string, generated by `TokenModule.generate_refresh_token()` |
| Storage | SHA-256 hash in `refresh_tokens` table — plaintext never stored |
| Expiry | 30 days |
| Rotation | New token issued on every use; old one revoked with `replaced_by_token_hash` pointer |
| Family tracking | `family_id` groups tokens from one login chain |
| Reuse detection | Presenting an already-revoked token should trigger full family revocation (verify this is wired in `refresh_access_token()`) |

Sent to `POST /auth/refresh` in the request body — not as a cookie.

## 3. Authentication Flows (Actual)

### 3.1 Registration (Single Step)

```
POST /auth/register
Content-Type: application/json

Body:
{
  "email": "alice@example.com",
  "username": "alice",
  "password": "correct horse battery staple 1!",
  "full_name": "Alice Smith",
  "signing_public_key": "base64url...",
  "exchange_public_key": "base64url..."
}

Server:
1. Validate password strength (PasswordModule.validate_strength)
2. Check email_exists() and username_exists()
3. Hash password (Argon2id)
4. create_user() — single INSERT including signing_public_key, exchange_public_key
5. Send verification code to email (store SHA-256 hash, 10-min TTL)
6. Audit log "register"

Response: 202 Accepted
{
  "message": "Registration complete. A verification code has been sent to your email."
}
```

Note: keys are generated client-side **before** this call and sent in the same request — there is no separate `/api/register/keys` step.

### 3.2 Email Verification (Auto-Login)

```
POST /auth/verify-email
Body: { "email": "alice@example.com", "code": "123456" }

Server:
1. Fetch user by id derived from email lookup
2. Compare SHA-256(code) to stored hash, timing-safe
3. Check expiry
4. mark_email_verified()
5. Issue access_token + refresh_token immediately

Response: 200 OK
{
  "requires_totp": false,
  "tokens": { "access_token": "...", "refresh_token": "...", "token_type": "bearer", "expires_in": 900 },
  "user": { "user_id_hex": "...", "username": "alice", ... }
}
```

The client is authenticated immediately after verification — no separate login step required.

### 3.3 Login

```
POST /auth/login
Body: { "email": "alice@example.com", "password": "...", "totp_code": null }

Server:
1. _check_login_lockout(email) — BEFORE password verify
2. get_user_by_email()
3. verify_password(password, stored_hash) — always runs (dummy hash if no user)
4. On failure: _handle_failed_login(), audit log, raise 401
5. On account_deleted / not is_active: raise 401
6. Opportunistic rehash if legacy PBKDF2 hash
7. If totp_enabled: return { requires_totp: true, user_id_hex }
8. Else: issue tokens, reset rate limit, audit log

Response: 200 OK
{
  "requires_totp": false,
  "tokens": { ... },
  "user": { ... }
}
```

### 3.4 TOTP Second Factor

```
POST /auth/verify-totp-login
Body: { "user_id_hex": "...", "totp_code": "123456" }

Server:
1. get_user_by_id_hex()
2. totp.verify_code(secret, code)
3. On success: issue tokens (same as normal login completion)

Response: 200 OK + tokens + user
```

### 3.5 Keypair Loading (Layer 2 — Client-Side Only)

No server interaction. Documented fully in `05-KEYSET_MANAGER.md`. Summary:

```
User uploads .medledger-key.json
→ KeysetManager.loginUser(username, keypair)
→ Validates format, derives user_id_hex, compares to server value (from /auth/me)
→ Private keys held in module memory
→ Vault: UNLOCKED
```

### 3.6 Token Refresh

```
POST /auth/refresh
Body: { "refresh_token": "..." }

Server:
1. hash_refresh_token() → lookup in DB
2. If not found or expired: 401 "Invalid or expired refresh token."
3. Rotate: generate new refresh token, store, revoke old (replaced_by_token_hash)
4. Issue new access token

Response: 200 OK
{ "access_token": "...", "refresh_token": "...", "token_type": "bearer", "expires_in": 900 }
```

Frontend should intercept 401 responses, call `/auth/refresh`, retry the original request with the new access token.

### 3.7 Logout

```
POST /auth/logout
Authorization: Bearer <access_token>
Body: { "refresh_token": "..." }  (optional)

Server:
1. If refresh_token provided: revoke that specific token
2. Audit log "logout"

Response: 200 OK { "message": "Logged out successfully." }
```

```
POST /auth/logout-all
Authorization: Bearer <access_token>

Server: revoke_all_user_refresh_tokens() — logs out every device
```

### 3.8 Password Change

```
POST /auth/change-password
Authorization: Bearer <access_token>
Body: { "old_password": "...", "new_password": "..." }

Server:
1. get_user_by_id_hex()
2. verify_password(old_password, stored_hash)
3. validate_strength(new_password)
4. hash_password_argon2(new_password) → set_password_hash() — single string, salt embedded
5. revoke_all_user_refresh_tokens() — forces re-login everywhere
6. Audit log "password_change"

Response: 200 OK { "message": "Password changed. Please log in again." }
```

**Keypair impact:** None. Password change never touches Layer 2. This is correct — Layer 1 and Layer 2 remain independent.

### 3.9 Password Reset

```
POST /auth/request-password-reset
Body: { "email": "alice@example.com" }

Server: Always returns the same response regardless of whether email exists
        (prevents user enumeration). If user exists, sends 6-digit code
        with 15-min TTL.

Response: 200 OK { "message": "If that email is registered, a reset code has been sent." }
```

```
POST /auth/confirm-password-reset
Body: { "email": "...", "code": "123456", "new_password": "..." }

Server:
1. Verify code hash + expiry (timing-safe)
2. validate_strength(new_password)
3. hash_password_argon2() → set_password_hash()
4. Clear used reset token
5. revoke_all_user_refresh_tokens()
6. Audit log "password_reset_confirm"

Response: 200 OK { "message": "Password reset successfully. Please log in." }
```

**Important:** This restores Layer 1 access only. If the user has also lost their keypair file, the vault remains permanently locked regardless of password reset.

### 3.10 TOTP Setup / Confirm / Disable

```
POST /auth/totp/setup        (JWT required)
  → generates secret + 8 backup codes (shown once, hashed for storage)
POST /auth/totp/confirm      (JWT required)
  → verifies live code, sets totp_enabled = true
POST /auth/totp/disable      (JWT required)
  → requires password + live TOTP code
  → revokes all refresh tokens
```

## 4. Session State Machine (Actual)

```
                    ┌─────────────┐
                    │  LOGGED OUT │
                    └──────┬──────┘
                           │ Register + verify email, or Login
                           ▼
                    ┌──────────────┐
                    │  LAYER 1 ONLY │
                    │  (JWT active) │
                    │  Vault: LOCKED│
                    └──────┬───────┘
                           │ Upload Keypair File (client-side, no server call)
                           ▼
                    ┌──────────────┐
                    │  FULLY ACTIVE │
                    │  Vault: UNLOCKED
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
        ┌─────────┐  ┌─────────┐  ┌─────────┐
        │ Refresh │  │ Logout  │  │ Lock    │
        │ Token   │  │         │  │ Vault   │
        └────┬────┘  └────┬────┘  └────┬────┘
             ▼            ▼            ▼
        ┌─────────┐  ┌─────────┐  ┌─────────┐
        │ LAYER 1 │  │ LOGGED  │  │ LAYER 1 │
        │ ONLY    │  │ OUT     │  │ ONLY    │
        └─────────┘  └─────────┘  └─────────┘
```

## 5. Proof-of-Work (Actual)

```
GET /auth/pow/challenge
Server: issue_pow_challenge()
  - Generates challenge string
  - Stores in pow_challenges table with expiry
Response: { challenge_id, challenge, difficulty, timestamp }
```

```
POST /auth/pow/verify
Body: { challenge_id, solution }
Server: verify_pow_challenge()
  - Fetch challenge, check not expired
  - Verify SHA-256(challenge + solution) meets difficulty
  - Delete challenge on success (replay protection)
Response: { message: "Proof of work verified." } or 400
```

PoW is verified as a standalone step before registration in the current implementation — not embedded inside the register call itself. Frontend should call `/auth/pow/challenge` → solve → `/auth/pow/verify` → then `/auth/register`.

## 6. Rate Limiting (Actual)

Implemented via `rate_limit` table with `key_hash`, `action`, `attempts`, `first_attempt`, `last_attempt`, `blocked_until` columns.

| Action | Behavior |
|--------|----------|
| `login` | 5 failures → 15-minute lockout, keyed by SHA-256(email) |
| Reset on success | `reset_rate_limit()` deletes the row entirely |

Extend this pattern for other rate-limited actions (registration, password reset requests) by calling `upsert_rate_limit()` / `set_rate_limit_block()` with the appropriate `action` string.

## 7. CORS Configuration

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.medledger.com"],
    allow_credentials=False,  # No cookies used — Bearer tokens only
    allow_methods=["GET", "POST", "PUT", "DELETE", "OPTIONS"],
    allow_headers=["Content-Type", "Authorization"],
)
```

Note: `allow_credentials=False` is correct for the current Bearer-token pattern since no cookies are sent. If migrating to HttpOnly cookies (§9), this must change to `True` and `allow_origins` must list exact origins (never `*`).

## 9. Planned Hardening: HttpOnly Cookie Migration

This remains the recommended next step for production hardening. The original v2.0 cookie specification (access_token, refresh_token, csrf_token cookies with specific SameSite/Path settings) is still valid design guidance — see git history of this document for the full cookie table, Set-Cookie examples, and CSRF double-submit pattern. When ready to implement:

1. Switch `TokenModule` to set cookies instead of returning tokens in the response body
2. Add CSRF token generation and double-submit validation middleware
3. Update CORS to `allow_credentials=True` with exact origin allowlist
4. Update frontend to use `credentials: 'include'` instead of manual Authorization headers
5. Remove tokens from JSON response bodies entirely

This is a breaking change for any existing frontend integration and should be planned as a coordinated release.
